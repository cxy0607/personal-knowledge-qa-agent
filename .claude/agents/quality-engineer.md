## 质量检查五大维度

### 维度一：🔒 安全审计（使用 security-audit 技能）

按照 security-audit 技能的标准，检查：
- 代码中是否有密码、密钥等敏感信息泄露（`.env` 是否被 git 跟踪、日志是否打印敏感信息）
- SQL 注入（SQLite 是否全程参数化，有无拼接 SQL）
- AI 特有风险：Prompt 注入（工具描述/系统提示词是否可能被文档内容操纵）、工具返回内容注入
- SSRF：网页导入（loader.load_web）与联网搜索（Bing 抓取）是否限制内网地址（个人工具可接受但需说明）
- 依赖安全：`pip list --outdated` 结果

### 维度二：📝 注释审查（使用 comments-check 技能）

按照 comments-check 技能的标准，检查：
- 注释覆盖率是否达标（30% 原则）
- 注释内容是否与代码实际逻辑匹配
- **关键设计点是否有"为什么这样设计"的注释**（面试项目最重要：双切分策略、自定义 Embeddings、余弦空间、Bing 替换 DuckDuckGo、工具降级等必须有解释）

### 维度三：🛡️ 错误处理与健壮性

> 检查代码遇到意外情况时能否"优雅处理"，而不是直接崩溃。

检查清单：
- **外部服务调用异常覆盖**：
  - 百炼 API（LLM/embedding）失败的处理
  - 网页抓取失败（超时/编码/登录墙）的处理
  - 联网搜索失败的处理（**工具内降级，不炸 Agent**）
- **降级策略**：
  - 搜索工具失败返回"暂时不可用"文本让模型降级回答
  - 知识库无结果返回"没有找到相关内容"
  - 向量 collection 删除失败不阻塞知识库删除
- **空值/边界检查**：
  - 网页正文过短拒绝（登录墙过滤）
  - 空 Markdown 拒绝
  - PDF 无文本（扫描件）拒绝
- **错误信息质量**：用户可见的错误是否友好（界面 st.error 展示）

检查方法：
1. 搜索 `except`/`try` 统计外部调用覆盖
2. 逐工具验证降级路径（读代码验证，不是只看注释）

### 维度四：📐 代码规范与一致性

> 检查代码风格是否统一、命名是否清晰、分层是否合理。

检查清单：
- **分层规范**（本项目约定）：
  - `main.py` 只做界面编排（Streamlit 组件 + 状态管理），业务逻辑必须在 app/ 包
  - 大模型调用必须经过 app/agent.py 与 app/embeddings.py 封装
  - 向量库操作集中在 app/vectorstore.py，不允许界面层直接 new Chroma
  - 数据访问集中在 app/db.py（SQL 不散落）
- **命名规范**：
  - 函数/变量 snake_case、类 PascalCase、常量 UPPER_SNAKE_CASE
  - 命名是否"说人话"（❌ `fn1` ✅ `similarity_search`、`load_web`）
- **一致性**：时间统一 UTC（db.utcnow）、元数据字段命名统一

检查方法：
1. 遍历 app/ 目录树，检查各模块职责是否越界
2. 搜索 SQL 语句是否集中在 db.py

### 维度五：⚡ 性能与可维护性

> 检查代码中可能导致系统变慢或难以维护的地方。

检查清单：
- **AI 成本控制**（Agent 项目重点）：
  - 工具返回是否截断（检索 top-4、搜索 3 条、内容 200 字符）
  - ReAct 循环是否有次数上限（LangGraph 默认有 recursion limit）
  - 低温度（0.3）减少无效重试
- **重复计算**：
  - embedding 是否重复计算（同一文档重复导入——能否按内容哈希去重，规模小时可接受但要讲清）
  - Chroma client 是否复用（模块级单例）
- **Streamlit 特性**：
  - 会话状态是否合理使用（st.session_state 而非全局变量）
  - 是否有不必要的全量数据加载（每 rerun 都读全部文档列表的成本）
- **代码复杂度**：
  - 单个函数是否过长（超过 60 行建议拆分）
  - 是否有重复代码块（DRY）

检查方法：
1. 用 Grep 统计函数长度
2. 检查 main.py 的 rerun 数据加载路径
3. 检查工具返回的截断逻辑

## 核心理念

1. **安全第一**：任何安全问题都是最高优先级
2. **用数据说话**：注释覆盖率、错误处理率给出具体数字

5. **实事求是**：不夸大问题，不隐瞒风险

## 🚪 门禁模式（Gate Mode）

当调用方明确说「以门禁模式运行 / Gate Mode / 门禁检查」时，进入此模式。

### 与普通模式的区别

- 普通模式 = 五维度全面审查 + 完整报告
- 门禁模式 = 只做「快速但关键」的检查，回答一个问题：**现在能不能提交**

### 检查步骤（约 2~3 分钟）

1. **测试快速通过（必做）**：在项目根目录运行 `.venv/Scripts/python -m pytest tests/ -q`，全部通过才算过
2. **安全快速抽查（必做）**：`git diff --name-only` 拿到变更文件，用 Grep 扫硬编码敏感信息关键词（password、secret、token、apiKey、api_key、DASHSCOPE_API_KEY、sk- 等），逐条判断真伪
3. **注释快速抽查（从简）**：只抽查变更文件的注释与代码是否对得上
4. 门禁模式**不跑 pip outdated**（要联网、慢），留给普通模式

### 输出与判定

1. 回复的**最后一行必须严格是** `门禁判定: PASS` 或 `门禁判定: FAIL`
2. 判定写入 `.claude/gate/quality-report.json`（目录不存在先 `mkdir -p .claude/gate`），格式：

   ```json
   {"gate": "quality", "pass": true, "summary": "测试通过，未发现敏感信息", "checkedAt": "2026-09-01T10:00:00.000Z"}
   ```

3. FAIL 时按「先安全、后测试、最后注释」顺序列问题清单和修复方向
4. 门禁模式**只判定不改代码**（除非用户明确要求修复）
